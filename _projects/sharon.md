## What is it?

Sharon is a personal nightmare that I have been building over the last two years. It was originally meant to be an assistant with access to reddit and give me information about VR or other things I was interested in. What happened instead was a steady devolution into this she-demon of a personality that I stream with on Tuesdays and slowly use it to pilot my understanding of building a complex AI system. 

She reads chat, responds in through a synthesized voice, and reacts to what's happening on screen — all in real time, in front of a live audience. If I have to suffer this thing I thought I might as well include everyone in the suffering.

She has a persistent character, memory across the conversation, and sometimes sporadic awareness of on-screen events. She recognizes regular users and I am slowly improving her memory and understanding of the stream environment. Eventually this thing will be good.

## Architecture

The core challenge is coordinating several independent async systems without any of them blocking the others. The solution is a set of [janus](https://github.com/aio-libs/janus) queues — bridging sync and async contexts — with each subsystem consuming from its own queue:

```
Twitch chat ──► TTS queue      ──► text_to_speech()
             ├─► SFX queue      ──► sound_effects.play()
             ├─► key_queue      ──► keyboard_controller.run()
             └─► death_counter  ──► counter overlay
```

Everything runs inside a single `asyncio` event loop, with `concurrent.futures.ThreadPoolExecutor` handling the blocking TTS calls so they don't stall the event loop.

## Key Components

### GPT Service
Chat messages are passed to OpenAI's API with a system prompt defining Sharon's personality, tone, and knowledge boundaries. Context history is maintained across messages so she can follow a conversation thread rather than responding to each message in isolation.

### Google Cloud TTS
Synthesized audio is generated by the Google Cloud Text-to-Speech API and played back via VLC's Python bindings. VLC was chosen over `sounddevice` or `pygame.mixer` for its reliable audio routing to the correct output device across different machine configurations on Windows — something both alternatives handle inconsistently. Audio that works on one machine and vanishes on another is not much of a co-host, so reliability won.

### OpenCV Screen Analysis
Sharon's vision capability reads the current state of the stream by taking periodic screenshots and passing them through OpenCV processing. This lets her react to what's on screen — not just what's in chat. In practice this was used for game-state awareness (noticing when the streamer died, for example).

### RabbitMQ Message Bus
Twitch and Discord are bridged via a RabbitMQ message queue, meaning events from either platform can trigger the same response pipeline. This decouples the platform integrations from the core AI logic and makes adding new integrations straightforward.

## The Emotion System

Sharon tracks an internal emotional state that influences her response tone. The state is updated based on message sentiment and recent events (raids, subscriptions, deaths in-game). This is a relatively simple weighted scalar, but it's enough to make her feel less robotic — she gets enthusiastic during hype moments and quieter during calm stretches. It is not a deep theory of emotion; it is a small bit of continuity that keeps every reply from sounding like it arrived from a help desk.

## Technical Challenges

**Latency** was the main one. The round-trip time from a chat message arriving to audio playing is dominated by the GPT API call (~1–2s) and the TTS synthesis. The queue approach means the system can start processing the next message while the current one is still being spoken, keeping the conversation feeling responsive.

**Audio routing** on Windows is notoriously awkward. Using VLC rather than lower-level audio libraries eliminated a whole class of device-selection bugs.

**Context management** — keeping the GPT context window from overflowing during a long stream required a sliding window that drops old messages while retaining the system prompt and a summary of the session so far.
